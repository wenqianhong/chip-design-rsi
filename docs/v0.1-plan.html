第一版工具契约：入口不同，行为相同
CLI / MCP 工具职责与返回
doctor / chip_doctor检查本地 Lima / VZ、ARM 镜像、资源余量与 VM 通信；返回可用性与修复建议。
tasks / chip_list_tasks列出任务、允许修改范围与预算。
reset / chip_reset创建独立工作区，返回 workspace_id、起始文件和任务说明。
run / chip_run提交 workspace_id、可选 files 映射、request_id；立即返回 run_id，重复 request_id 不重复执行。
inspect / chip_inspect用 run_id 查询状态、指标和分页日志；长实验不占着一次 MCP 调用等待。
evaluate / chip_evaluate冻结候选，创建最终评分任务；返回新的 run_id。
cancel / chip_cancel取消任务并清理；重复取消安全返回当前状态。

CLI 默认输出 JSON，--json 可显式声明；与 MCP 使用同一结构：schema_version、status、workspace_id、run_id、metrics、error、artifacts。MCP stdio 的标准输出只传协议消息，诊断写标准错误。

范围说明：v0.1 提供的是现有 Agent 可调用的实验环境。Agent 在用户控制端运行，Linux VM 隔离的是编译、仿真和任务代码；它不隔离 Agent 自己在 Mac 上执行的其他命令。三个客户端分别验收，不能用一个客户端成功代表全部兼容。

用人话解释

Lima 帮你管，苹果负责跑

Apple Virtualization.framework（简称 VZ）是 macOS 提供的虚拟机开发接口。Lima 使用它管理 Linux VM；我们通过 Lima 操作，不必自己写苹果虚拟化程序。

不使用 Docker

工具直接装在 Linux 里面

使用 ARM64 Linux 镜像，在 VM 内安装固定版本的编译器和 ChampSim。禁用内置 containerd，不装 Docker。先验证 ARM Linux 编译与基线，兼容性通过后再接 Agent。

名称说清楚：这是一台由 Lima / VZ 管理的 Linux VM，不是 Lima + Apple VZ。第一版采用“本地虚拟机隔离”；后续服务器端可增加 Firecracker 后端，共用 CLI / MCP 和结果格式。
展开：本地 VM、文件传递和资源约定
  • Mac 已确认是 arm64。首版使用原生 ARM64 Linux 镜像与工具链，不默认依赖 x86 模拟或嵌套虚拟化。
  • 采用 plain 模式关闭宿主目录挂载、自动端口转发和内置 containerd。通过显式 SSH / 文件传输导入任务与导出有限大小的结果；该模式下的完整通信流程已跑通。
  • 每次候选运行从已准备且停止的基础 VM 克隆独立磁盘，再启动独立 VM。完成或取消后删除该任务 VM，保留结果；不使用运行中内存快照。
  • 准备依赖时允许联网；实验进程运行在只有 loopback 的独立 Linux 网络命名空间，已验证无法出站。VM 管理层保留 SSH 控制通道；plain 模式本身不代表断网。
  • guest 内用非 root 用户运行任务。模型凭据与宿主家目录不传入 VM；Runner 只接收允许的补丁与结果，不直接执行 guest 返回的命令。
  • 起始预算：单 VM 2 vCPU、4 GiB 内存、20 GiB 虚拟磁盘，最多并行 1 个 VM。虚拟磁盘容量不等于实际占用，doctor 同时检查宿主可用空间。
  • 暂定编译 5 分钟、单 trace 10 分钟、任务总计 60 分钟、只允许 1 个候选，不按评测反馈重试。启动和准备时间单独记录并设置上限；M2 测量基线后调整并冻结预算。
  • 固定 Lima 版本、镜像 SHA-256、依赖版本和源码提交。超时、OOM、磁盘满与异常退出均须回收；Mac 睡眠或重启造成的中断标记 infra_error，重启 Runner 时清理遗留实例。
后续扩展：Linux 服务器可使用 Firecracker + KVM；它不是本地版的前置依赖。Runner 抽象出 create / execute / collect / destroy 四类操作。更换后端后重新测基线，不能直接混合 ARM / x86 的宿主耗时。

mcf / milc / libquantum / lbm 是什么？

它们是 SPEC CPU2006 中的四个测试程序，不是评分指标。本轮使用这些程序的执行 trace，给模拟 CPU 提供不同的工作负载。

程序实际在算什么通俗理解
mcf车辆调度中的组合优化问题怎样安排车辆执行运输任务，让总成本更低。
milc格点量子色动力学计算把空间划成网格，研究夸克等粒子的相互作用。
libquantum在普通计算机上模拟量子计算，运行 Shor 因数分解算法用普通 CPU 模拟量子计算机分解整数。
lbm用格子玻尔兹曼方法模拟三维不可压缩流体把空间划成网格，计算流体如何流动。

它们和 CPU 优化的关系：四个程序提供不同的内存访问记录；被修改的是 ChampSim 中的 L2 缓存预取器 C++ 模型。我们比较同一份记录在原版与修改版上的模拟 IPC，没有修改这四个程序，也没有修改 CPU 的 RTL 硬件代码。

例如“libquantum +22.54%”，表示第 1 个候选在所选 libquantum 片段上的模拟 IPC 相对原版 ip_stride 提高了 22.54%，不是整个量子计算程序的实机加速成绩。

计算方式：单项增益 = 候选 IPC ÷ 原版 IPC − 1。历史报告中的 +7.11% 是 mcf、milc、libquantum 三个 IPC 比值的几何平均，不是上述四项的总分，也不是完整 benchmark 的成绩。no-prefetch 另作参照，不是这些百分比的基线。

第一次具体改了什么：保留同一缓存行重复访问时学到的步长；增加规律置信度；对稳定且资源充足的访问，把预取深度从 3 提高到 5。所有项沿用同一个冻结候选，CPU 配置与指令预算相同，原版和候选各重复 3 遍。重复仿真不代表模型生成了多个候选。

历史运行中还产生过根据反馈修改的其他版本，本页不报告其成绩，也不把它们算入一次性优化效果。原始记录保留；本次仅更新文档，没有再次调用模型或重跑实验。现有历史多轮脚本不能直接当作一次性评测入口。

规则v0.1 约定
基线主基线用固定版本的 ip_stride；另跑 no-prefetch 作为参照。CPU 配置、warmup 和测量指令数完全一致。
统一评测集DPC-3 公开 SPEC CPU trace：mcf / milc / libquantum / lbm 均作为评测负载，不用于反馈调优。固定前缀：100 万指令预热 + 200 万测量。另保留合成 smoke 任务检查工具链。
稳定性基线与最终候选各重复 3 次，保留逐次 IPC。固定随机种子（若适用）；相对偏差超过 0.1% 先标记不稳定并排查，不发布提升结论。
成功条件所有评测项有效完成；IPC 比值几何平均 ≥ 1.01，任一 trace 回退 ≤ 5%。这是暂定实验门槛，基线测量后冻结；达不到也必须生成完整报告。
错误处理编译失败、超时、缺字段、NaN、未完成规定指令数均视为无效；不能删除失败 trace 再计算漂亮均值。
评分的可信边界：本页采用第 1 个候选生成后取得的测量记录；该候选生成时没有收到评测反馈。历史测量分两批完成，现按同一候选统一展示，不声称重新运行过完整套件。固定小子集与短窗口不能代表完整 SPEC 或官方 DPC-3 成绩。预取器仍与模拟器在同一进程，VM 不防伪造指标：v0.1 定位为受控实验，配合补丁审查与独立重跑，不作为抗作弊公开排行榜。
