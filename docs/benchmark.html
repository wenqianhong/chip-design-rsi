展开一个容易看懂的例子

人为构造的格式示意，不是本轮真实 trace 摘录。下面把一条二进制记录转写成 JSON，方便阅读；实际文件里没有字段名和大括号。

{
  "ip": "0x400100",
  "is_branch": 0,
  "branch_taken": 0,
  "destination_registers": [1, 0],
  "source_registers": [2, 0, 0, 0],
  "destination_memory": ["0x0", "0x0"],
  "source_memory": ["0x800040", "0x0", "0x0", "0x0"]
}

意思是：代码位置 0x400100 的指令不是跳转；它依赖编号 2 的寄存器，产生编号 1 的寄存器结果，并读取数据地址 0x800040。空槽位用 0 表示。单靠这些字段不能还原完整机器指令或读到的数据值。

展开开发者解码方式
import lzma, struct
record = struct.Struct('<QBB2B4B2Q4Q')
assert record.size == 64
with lzma.open('example.champsimtrace.xz', 'rb') as f:
    raw = f.read(64)
    if len(raw) != 64:
        raise ValueError('不完整的指令记录')
    values = record.unpack(raw)
    ip, is_branch, taken = values[:3]
    dst_regs, src_regs = values[3:5], values[5:9]
    dst_mem, src_mem = values[9:11], values[11:15]

< 表示小端，Q 是 8 字节无符号整数，B 是 1 字节无符号整数。

mcf / milc / libquantum / lbm 是什么？

它们是 SPEC CPU2006 中的四个测试程序，不是评分指标。本轮使用这些程序的执行 trace，给模拟 CPU 提供不同的工作负载。

程序实际在算什么通俗理解
mcf车辆调度中的组合优化问题怎样安排车辆执行运输任务，让总成本更低。
milc格点量子色动力学计算把空间划成网格，研究夸克等粒子的相互作用。
libquantum在普通计算机上模拟量子计算，运行 Shor 因数分解算法用普通 CPU 模拟量子计算机分解整数。
lbm用格子玻尔兹曼方法模拟三维不可压缩流体把空间划成网格，计算流体如何流动。

它们和 CPU 优化的关系：四个程序提供不同的内存访问记录；被修改的是 ChampSim 中的 L2 缓存预取器 C++ 模型。我们比较同一份记录在原版与修改版上的模拟 IPC，没有修改这四个程序，也没有修改 CPU 的 RTL 硬件代码。

例如“libquantum +22.54%”，表示第 1 个候选在所选 libquantum 片段上的模拟 IPC 相对原版 ip_stride 提高了 22.54%，不是整个量子计算程序的实机加速成绩。

来源：SPEC 官方程序介绍

拿什么来测？

直接使用 DPC-3 公布的 SPEC CPU trace。trace 是程序执行记录；ChampSim 根据这些记录模拟 CPU、缓存和内存，不需要在 Mac 上重新编译 SPEC 程序。

谁负责什么？

Codex 改代码 → VM 编译仿真 → 控制器核算 → 反馈下一次

Codex 只能修改 ip_stride.cc / ip_stride.h。控制器锁定 trace、指令数、CPU 配置与评分；沿用原版 ip_stride 作主基线，同时跑 no-prefetch 作参照。模型不能通过自己的文字声明判定成功。

选型规则预先固定：优先在“每个开发负载回退不超过 5%”的候选里选 IPC 比值几何平均最高者；没有候选满足时，保留有效候选中平均最高者，但必须报告未通过。成功门槛：几何平均至少 +1%，单项回退不超过 5%。

实测结果 · 3 次开发 + 1 次冻结验证

第 1 次：保留重复访问间的规律，对稳定访问增加预取距离。第 2 次：增加重复预取过滤，未带来额外 IPC 收益。第 3 次：规律变化时取消旧预取，开发均值反而略降。因此选择第 1 个候选。
