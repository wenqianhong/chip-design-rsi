01 · V1.0 到底交付什么？

交付 A

可独立评测的工程任务

把岗位 JD 拆成具体工作项，而不是“一道题当一个工程师”。每题有冻结输入、允许操作、实际产物和可执行验收。

交付 B

多模态 benchmark

复用已有设计、测试和任务集；缺的再合成。包含代码、原生图形模型、波形与物理视图，评测真实工程操作。

交付 C · 工作特色

整体 co-design 任务

同一个设计贯穿系统模型、RTL、实现与最终检查，允许在规定边界内联合取舍；结果便于人理解和继续修改。

三条线同时合格：功能正确 × 工程指标达标 × 设计可读可编辑。缺一项不能只靠漂亮图或高分报告宣称成功。

范围：以数字 CPU / 子系统为主线；先用小型同源设计验证连接，再进入 CPU 子系统任务。模拟电路、DFT、CDC/低功耗、EM/IR 等按工具与数据成熟度扩展；真实制造、ATE、回片与良率不虚构仿真标签。V1.0 不包含模型训练。

28 个岗位的职责覆盖远大于本轮能力：岗位清单。以下是拟建设任务族，均不因 v0.2 的小样例跑通而自动视为已有 benchmark。

02 · 先把任务合同写清楚

任务族对应岗位模型收到什么允许做什么怎样判定完成数据怎么来
T01 · 规格 → 系统模型J01–J02需求、工作负载、接口、框图与可编辑模型模块划分、连接、参数和预算模型可执行；接口一致；需求有验证项；框图可读已有设计规范优先；缺失的合法变体再合成
T02 · 微架构 / RTL 设计与优化J02–J04同一设计的 RTL、数据通路、约束、性能记录逻辑、流水线或允许修改的结构功能不变或符合新规格；性能/PPA 对比配置一致复用 PicoRV32 等候选设计；先核对许可、测试与修改边界
T03 · 波形调试 / 功能验证J05–J06RTL、波形、断言、测试与失败上下文修复设计；补充指定验证产物独立参考检查；回归无退化；反例解释与实际位置对应复用上游测试；注入受控错误并验证题目可解
T04 · 综合 / 映射 / 约束J09、J11网表结构、库、SDC、时序路径和报告允许的 RTL、约束或综合配置一致性/等价检查；不允许靠放宽目标获得“增益”复用综合样例和库；生成预算/配置变体
T05 · 布局 / 时钟树 / 布线J10可交互 floorplan、层次、拥塞、引脚与关键路径合法的布局决策、约束、物理参数连通、物理规则、时序与资源预算；空间问题可定位复用 OpenROAD 样例；初始布局与约束变体需实际跑通
T06 · 时序 / 功耗 / 物理检查J11–J13角点、寄生、路径、热点、规则和电源场景修复允许范围内的工程问题固定模式/角点/活动场景；约束审计；LVS/功耗能力缺失即标缺失时序/DRC 可先做；功耗、EM/IR、LVS 先补验证能力
T07 · 设计审查与可读性交付贯穿 T01–T06原生设计、视图、层次、命名、跨视图引用整理工程模型与视图；提交可追踪的审查说明语义未变；关键对象易定位；可编辑；不能只美化截图同一设计生成展示变体；配合真实定位/修改任务评测
T08 · 同一设计的全流程 co-design上述任务组合统一工程包、系统目标、功能规格、工具预算联合调整结构/RTL、实现与可视化交付最终功能、PPA、规则与可读性共同验收；所有产物同源由已验证单任务组合；必须整体执行，不能拼接不同电路的日志
任务划分门禁：每题先证明“规格不歧义、输入足够、至少有一个已验证可行解、失败能识别”。错误定位题与设计优化题分开；未知是否可解的题不能混入正式计分集合。

DFT（J08）、CDC/低功耗（J07）、模拟设计（J15–J16）、制造与量产（J20–J28）目前没有对应成熟评测器；列入能力缺口，不承诺本版覆盖全部岗位。J14 的交付清单与 J19 的可复现流程作为所有任务的共同要求。

03 · 视觉输入和交付可读性，从第一天设计

按任务提供多种视图，不能只扔日志

系统框图/数据通路、带信号名与时标的波形、带坐标和图层的 floorplan、关键路径与拥塞视图。提供总览、局部和对象标识；图片与原生工程数据共享版本，点击对象可对应代码、模型或物理实例。

图像不是随意装饰，也不是把文本截图后算“多模态”。视觉密集任务必须能进行有意义的定位、比较与操作。

需要 Simulink 类能力：图本身就是模型

目标能力是可编辑模块、端口、连接、参数与层次，并能执行、检查和追溯到实现。可视化工程文件必须保留，不能只提交截图。V1.0 先定义中立的模块/连接/参数接口，并做一个可运行示范。

Simulink 的具体接入待验证：若选择现有工程与许可，验证原生文件读取、修改、运行和导出；自建图形前端只能承诺明确的模型子集，不能声称等同 Simulink。架构模型到 RTL 的自动转换也需单独验收。

工程师能看懂、找到问题、继续改

框图/原理图需要合理层次、明确命名、端口方向、分组和可追踪连线。物理版图提供分层、缩放、图层选择、对象搜索与关键路径/违规高亮，不要求把真实密集版图画成稀疏示意图。

提交原生工程、默认可读总览、关键局部视图、修改说明和验证证据。可读性不能通过删除重要模块、隐藏违规或篡改实际连线来获取。

自动检查

标签重叠/裁切、对象缺失、图与模型不一致、命名缺失、关键对象无法定位、不可打开/编辑、视图版本不匹配。连线交叉等指标只在适用的框图场景中使用。

工程可用性评测

让评审者完成“找到某路径、解释某异常、完成一个局部修改”的固定任务，记录成功率、时间和错误数。采用预先公布的评分准则与盲审；不以模型自评或主观美观分替代工程验收。

04 · 先复用，再合成；最后执行出真标签

1 / 资产盘点

现成题优先保留

区分 benchmark、参考设计、测试台、工艺库和工具回归样例。记录来源、许可、精确版本、下载方式与已知泄漏风险；候选资产未审核前不纳入正式发布。

2 / 受控生成

有意改变工程条件

生成合法参数、接口、预算、结构、布局初态或已知错误变体。保留生成过程与种子；参考方案在目标工具下实测可行，重复与等价变体去重。

3 / 真实执行

工具结果作为标签

运行功能、综合、物理与检查；收集退出状态、数值、产物哈希和图形证据。无效约束、超时、工具错误、功能失败和物理违例分别记录。

已有资产V1.0 复用方式不能冒充什么
DPC-3 trace / ChampSim独立微架构任务与历史基线短 trace 分数不是官方成绩；C++ 模型不自动成为可综合 RTL
PicoRV32 RTL / 固件CPU 任务的候选种子，补齐参数、接口与独立检查固件通过不是完整 CPU 形式化证明
OpenROAD GCD / Nangate45物理任务种子与工具接通参考与 PicoRV32 不是同一设计；不能拼为一个全流程样本
自写计数器 / 线宽错误检查评测器是否正确工作的控制用例不靠大量简单变体充当有难度的工程 benchmark

隔离规则：协议调试样本与正式测试按设计家族/结构分组隔离，不能只换位宽就随机分两边。协议调试是我们校准评测器，不是让被测 Codex 练习。公开题可能已被模型见过，应与新生成、未公开测试分别报告。

一条样本 =
任务合同 + 冻结输入 + 原生模型/图形视图
+ 允许修改范围 + 工具/工艺/约束/预算
+ 独立参考解与验收器（评测侧保管）
+ 生成谱系/版本/hash + 实际运行证据
+ 功能/工程/可读性结果 + 明确失败类型

05 · 单任务通过后，直接合成同一设计的全流程

先统一，再扩大

用一个小型同源设计证明各阶段交接正确；随后冻结一个小 CPU 子系统家族作为全流程主线候选。需实际审查接口、存储器、初始化、软件与约束可支持性后选定，不能只靠已有 PicoRV32 仿真推断后端一定可用。

系统模型与 RTL 至少用接口和行为测试校准；若不能建立可靠映射，先报告 RTL→物理的范围，不声称已实现架构到硅的全链路。

co-design 要证明联合取舍有效

例：流水线变化同时影响延迟、频率、面积与布线。模型必须在固定功能、吞吐/延迟约束下提交可实现的整体方案。对比“只改 RTL”“只调物理参数”“允许跨阶段修改”，而不是把工具顺序串起来就称协同设计。

修改上游即使下游产物失效，必须重新生成并验收；一次提交中不能混用不同版本的网表、寄生或图片。

06 · 先保留一次性评测，反馈研究单独列

协议模型能看什么输出与计分状态
A · 主评测：无反馈一次提交冻结输入与初始证据；不提供候选评测结果让模型重改第一次提交冻结后执行所有验收；失败也计入；无 best-of-3、无事后挑最好沿用用户已确认规则
B · co-design 工具反馈实验拟允许读取开发工具/中间阶段结果；隐藏测试与最终评分不可见固定总工具/时间预算；单独报告，不能与协议 A 混算可选研究协议；执行前需单独明确授权与反馈边界

co-design 的修改范围可以跨阶段，而评测是否提供反馈是另一件事。V1.0 先支持协议 A 下的跨阶段联合提案；不会为了“闭环”擅自改变一次性评测要求。使用用户自己的 Codex CLI 额度，暂不接 Claude 或其他模型。

先检查有效性

功能、规格、约束和产物一致性先过门禁，再报告 PPA。不能删除功能、减少测试、放松时钟或隐藏违规换分。

分项报告，不掩盖失败

报告任务成功率、各阶段失败、PPA 相对基线变化、视觉定位/编辑成功率、可读性与总成本。面积/功耗/频率注明场景，不随意合成一个总分。

做三组有解释力的比较

文本/结构数据 vs 加视觉；单阶段修改 vs 跨阶段修改；现成基线 vs Codex 首次提交。匹配任务、工具与资源预算，记录随机性和测量波动。

独立任务重复可用于估计稳定性，但每次都只能计首次提交，不能从多个输出挑最好。基础设施故障与设计失败分开，重跑条件在正式评测前冻结。

07 · 开源或 Cadence，是可切换的执行后端

现有开源后端：先提供可审计基线

复用 Icarus/Verilator、Yosys、OpenROAD/OpenSTA、KLayout 与公开平台。当前局限：样例分散、工业规则缺失、LVS 未运行、功耗等覆盖不完整。对这些限制直接标注，不以“已安装”冒充工业可信度。

本地仍采用 Apple VZ / Linux VM，不用 Docker。当前 GCD 原始时钟约束有 setup 违例，保留事实，不为获得通过而更改验收目标。

商业后端：按任务价值验证后接入

若公开模型或工具无法满足目标任务，就评估 Cadence 等授权工具后端。前提是工具可用、许可证与工艺资料适用、运行平台兼容、产物可导出；先用少量共同设计检查结果与差异。

工具服务化只负责提交任务、执行、取回原生产物和视图。Cadence 不自动解决任务定义、视觉界面或 co-design；购买服务、使用付费算力或接入受限资料不是本计划的自动执行授权。

同一任务合同可以接不同工具，但标签必须注明后端/工艺/版本。换工具后重新校准参考值；没有相关性证据，不把两套工具的结果直接混成同一个排行榜。

08 · 按交付门禁推进，不用虚构工期

P1

任务划分 + 资产审核

冻结任务族、输入输出、操作边界、视觉需求、来源与基线；区分已有 benchmark 和待包装样例。

交付：任务目录、资产/许可表、覆盖缺口、协议 A。
门禁：每个首批任务族至少有一个可执行参考任务。
P2

单任务数据 + benchmark

实现受控生成、原生模型/视图、独立验收、谱系去重和家族隔离；先验证评测器，再扩题量。

交付：版本化单任务集合、工具适配器、控制用例、baseline 报告。
门禁：已知正确、已知错误、超时和缺依赖都能正确区分。
P3

直接进入全 pipeline 合成

统一设计、接口、规格与工艺；搭建阶段依赖和产物失效管理；加入端到端可读性交付。

交付：同源全流程样本、完整工件包、全阶段证据。
门禁：至少一个参考设计端到端实测满足其冻结约束，跨阶段版本一致。
P4

co-design benchmark 与对比

冻结允许的联合设计空间；用自己的 Codex CLI 做一次性评测；完成视觉与跨阶段消融比较。

交付：失败也保留的结果、分项指标、人工审查记录、复现实验包。
门禁：能区分工具能力、视觉贡献和跨阶段设计贡献；不要求模型必须提升。

样本量和时间/调用预算在 P1 的代表性试运行后固定并登记，再运行正式测试；本页不把未经测量的数量或预算写成承诺。每个可验收阶段提交并推送 GitHub。
