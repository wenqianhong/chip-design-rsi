模块已经跑到哪一步？

先用固定样例证明工具能运行、结果能判对错。每张卡代表独立模块；它们目前还不是同一个 CPU 的全链路。

本阶段没有调用模型、没有训练，也没有拿评测反馈让 Codex 重改设计。使用 Mac 的 Apple VZ Linux 虚拟机，不用 Docker。

M2 · RTL 仿真

两种仿真器通过

PicoRV32 原版固件分别在 Icarus 和 Verilator 下通过。计数器也完成回绕、保持和复位检查。

M3 · 验证

能识别故意错误

语法错误会编译失败；把计数 +1 改成 +2 后，测试和形式化证明都识别出了错误。形式化范围是小计数器，不是整个 CPU。

M4 · 综合

网表行为通过

Yosys 已生成 PicoRV32 和计数器网表；综合后的 PicoRV32 重新跑原版固件并通过。计数器另完成 Nangate45 标准单元映射，并通过相同测试；仿真单元模型由 Liberty 生成，不含真实延迟。

M5 · 物理实现

准备工具中

OpenROAD 正在从固定源码编译。计划用上游 GCD / Nangate45 样例分别核对布局、时钟树、布线和产物；尚未报告通过。

M6 · 规则与时序

规则检查已部分通过

KLayout 已运行上游 FreePDK45 DRC 规则，接受正确线宽并检出违规线宽。时序与实际设计版图检查待完成；Nangate45 本地包缺 LVS 规则，未执行 LVS。

证据与复现

证据说明
15 项逻辑模块检查退出码、预期标记、命令、耗时和本地日志名
标准单元映射验收 / 超时清理验收映射后功能检查；超时后的子进程不会写入迟到结果
2 项 DRC 检查不是只看工具退出成功，还解析违规类别
正确图形报告 / 违规图形报告可在 KLayout 中打开
环境与源码版本 / 已安装工具版本源码固定 commit；输入文件记录 SHA-256
编译器兼容补丁新 GCC 的 ISA 标记需要显式 zicsr；没有修改 CPU RTL 或测试逻辑

已配置环境中运行：python3 scripts/modules.py logic 或 python3 scripts/modules.py drc，再执行 python3 scripts/modules.py collect。代表性日志：PicoRV32 门级仿真 / 标准单元映射 / 错误反例。完整日志和大型产物位于 .chipbench/modules/results/，不上传 VM 镜像和工具二进制。

这些结果证明工具模块可用，不代表 CPU 完整正确、真实工艺签核通过或已经可制造。计数器与线宽样例是工程验收，不作为模型能力 benchmark。
