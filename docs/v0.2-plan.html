01 · 每个模块先证明自己能工作

优先使用上游样例；可以使用不同的小设计
模块本版要跑通什么输入 → 输出独立验收依据
M0 · 环境与任务规格复用 Lima / Apple VZ；固定工具版本、参数、文件 hash 和资源预算。架构规格作为输入模板，不伪造“架构设计评分”。模块配置 + 输入文件 → 可运行实例 + 环境清单ARM64 兼容性、启动、日志、超时、清理均可验证；不用 Docker。
M1 · 微架构仿真整理已有 ChampSim 模块；保留原版预取器和固定 trace 的复现入口。C++ 模型 + trace + 配置 → 周期、IPC、缓存指标核对已有记录与解析器；环境变化或结果不一致时再重跑，不无故重复消耗。v0.1 有实测基础。
M2 · RTL 编译与仿真先用小型上游 RTL 样例，再跑小 CPU 的现成测试固件；确认仿真器与 RISC-V 工具链能工作。RTL + testbench + 必要程序镜像 → 结果、波形、周期已知正确样例通过；语法错误、错误输出和超时被明确区分。PicoRV32 是候选，不先承诺全部配置兼容。
M3 · 验证与调试接入测试断言 / 签名检查；用小型可证明样例调通形式化工具，CPU 级完整证明不作本版承诺。设计 + 测试 / 性质 → 通过、失败反例或无法判定正确样例通过；已知错误样例被发现；形式化超时或有界结果不能标成无条件证明。
M4 · 逻辑综合Yosys 用固定样例和脚本生成网表；选定平台后再测试标准单元映射。RTL + 库 + 综合约束 → 网表、单元统计、日志顶层正确、无未解析模块；资源统计可复查；做适用的前后功能 / 等价性检查。
M5 · 物理实现用 ORFS 上游小设计和固定输入，分别验证 floorplan、placement、CTS、routing、寄生提取与版图导出。经过确认的网表 + 库 / LEF + 约束 → DEF、布线网表、SPEF、GDS、布局图逐子步骤检查产物与日志。可以从上游完整样例获取中间输入，不要求接收 M4 的产物。
M6 · 时序与物理检查对已知样例运行 OpenSTA 及时序约束检查；选定平台支持时运行 KLayout 等 DRC / LVS 检查。网表 / 版图 + 库 + 约束 + 规则 → 时序、违规与连接一致性报告有效约束覆盖与检查范围可解释；故意过紧的时序或已知规则错误能被识别。缺规则或未运行不能写成通过。
“每个模块调通”不等于只安装成功。必须实际运行样例并核对结果。物理检查依赖平台提供的库和规则；不支持的检查标记 unsupported / blocked 并说明缺项，不把它计入已完成模块。正式工艺签核、制造和实测不在本版范围。

02 · 所有模块用同一套验收标准

能运行

一条可复现入口

固定输入、版本和命令；无需临时手工修改文件。原始日志、退出码、耗时和产物路径完整保存。

能判对错

成功与失败都测过

正确样例得到预期结果，已知错误能被识别。不能只看退出码或工具打印的 PASS；同时核对关键输出。

能复核

不透明结果不算完成

记录输入输出 hash、必要统计、适用范围与限制。超时、缺依赖、无法证明、不支持，分别标记。

确定性模块在固定输入下应得到一致结果；有随机步骤则固定并记录种子。资源和清理检查针对 Runner 做一次适当覆盖，各模块只补充其特有故障检查。模块通过后，不在没有改动或新问题时反复重跑。

统一记录格式：为以后串联留接口，不现在强行串联
module_id / tool_version / platform_version
input_files + hashes / parameters / random_seed
status = passed | failed | timeout | blocked | unsupported
checks = [{name, expected, observed, outcome}]
output_files + hashes / log / elapsed_time / resource_use
limitations / reproduction_command

03 · 按这个顺序推进

第一步

盘点已有环境与 M1

确认现有 VM 和 ChampSim 成果可以复用，整理版本和证据；测量可用资源。先明确新增模块的依赖。

第二步

M2 / M3：逻辑先算对

调通 Verilog 仿真、现成测试、断言与一个小型形式化样例。先小模块，再用小 CPU 固件检查工具链。

第三步

M4：生成真实网表

固定综合样例、顶层、库和约束；核对网表和资源。这里不调用 Codex 修改设计。

第四步

M5 / M6：实现与检查

用上游已支持的小样例调通物理各阶段与时序 / 规则检查。优先确认平台资料和 ARM64 工具兼容性，再决定安装路径。

本地执行原则：仍用 Linux VM，不用 Docker。工具缺 ARM64 预编译包时先核对源码构建路径；资源不足或平台不支持时记录实际阻塞，不声称已完成，也不擅自转到收费云端。

04 · v0.2 最后交付什么？

交付物内容
模块运行入口每个模块独立启动、读取输入、输出日志与产物；暂不强制接入同一条链。
固定样例与依赖清单上游来源、许可、精确版本、输入 hash、工具配置与平台说明。
模块验收记录逐模块通过项、失败项、阻塞项与复现命令；只有实测成功才勾选。
可视化 HTML在 docs 中展示模块状态、波形 / 布局示例、关键指标和证据链接；未经运行的模块明确标待实现。
后续拼接清单说明模块之间还缺哪些格式转换、约束统一和依赖；记录集成风险，不把集成提前算作完成。
版本完成标准：约定模块均有可复现实测及独立验收证据；未完成项如实列出。无需模型优化成功，也无需在本版完成一个 CPU 的端到端流程。

05 · 全链路放到后续版本

v0.2：独立模块先证明工具能运行、结果能判断
→
后续：串成一道任务统一设计、约束、产物与阶段依赖
→
之后：任务集与研究一次性评测；训练需另设协议

后续再让同一个冻结候选依次经过 RTL 验证、综合、物理实现与最终评分。那时才加入完整任务状态机、模型一次生成控制和端到端对比。训练模型不是本版目标；如果以后训练，再单独处理训练奖励、任务划分与独立测试。
